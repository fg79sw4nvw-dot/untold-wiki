# プラットフォーム移植性・ストア対応方針

**状態：確定**  
**決定日：2026-09-16**  
**更新日：2026-09-16**

この文書は、UNTOLD v1を**ストア配布を正式な完成形**として開発しつつ、Web技術・Vercel・ブラウザ実行環境を開発・試遊・プロモーションへ再利用するための設計制約を定義する。

2026-09-16に従来の「まずSafari / PWA版を完成させ、必要なら後からストア対応する」方針を廃止した。以後は、**最初からストア版を製品版として成立させる**ことを前提とする。

---

## 1. 基本方針【確定】

- UNTOLD v1の正式な製品配布先は App Store / Google Play を基本とする。
- ゲーム本体の正規実装は TypeScript / Web技術を中心に維持する。
- Swift / Kotlin 等へゲーム本体を全面移植することは、別の明示的な判断がない限り行わない。
- Web版を先に完成させてからストア化するのではなく、開発初期からストア環境で成立する境界を維持する。
- iOSを第一基準環境として先行検証する。Androidでも再実装なしで展開できる構造を維持し、本格QAは開発後半で追加する。
- 現時点のネイティブラッパー第一候補は Capacitor とする。採用前・更新時には最新のApple / Google審査要件と技術状況を確認する。

## 2. 配布環境の役割【確定】

### ストア版

- 一般ユーザー向けの正式な製品版。
- App Store / Google Playで配布する。
- セーブ、OSライフサイクル、Safe Area、署名、ストア提出、更新互換性を含めて製品品質を判定する。

### Vercel / Web版

Vercelは廃止せず、以下の複数用途へ使う。

- 日常開発の高速プレビュー。
- GitHub `main` のブラウザ動作確認。
- 一般向けブラウザ体験版。
- プロモーション依頼先向けデモ。
- メディア／配信者等への限定プレビュー。
- 宣伝用映像・スクリーンショット確認用ビルド。

Vercel上の公開版をUNTOLD v1の正式製品版とは扱わない。製品版全体や終盤の重大なネタバレを、プロモーション目的だけでWebへ無制限公開することも前提にしない。

### TestFlight / Google Play テスト配布

- 実際のストアアプリ環境に近いベータ・QA用途。
- 節目の実機確認、先行テスト、リリース候補版の確認に使用する。
- Vercelの高速確認と役割を分け、日常の細かな修正ごとにストア配布工程を回さない。

## 3. レイヤー分離【確定】

UNTOLDは原則として以下の4層を分離する。

```text
コンテンツ定義
  カード / NPC / 会話 / 情報 / 依頼 / イベント / 世界データ
        ↓
ゲームロジック
  進行 / 条件 / 時間 / 記録 / 所持 / セーブ状態 / 移動計算
        ↓
表示・入力
  フィールド描画 / BOOK / UI / Pointer / Keyboard等
        ↓
プラットフォーム層
  Web/PWA / Capacitor / OS保存 / ライフサイクル / ストア固有機能
```

ゲームロジック層へ `window`、`document`、`navigator`、`localStorage`、Service Worker、iOS / Android固有API、ストアSDKを理由なく直接埋め込まない。

## 4. セーブと保存先【確定】

`pages/development/save-data-model.md` のセーブスキーマを保存媒体から独立させる。

- `SaveData` はゲーム状態の交換形式。
- 保存先はStorage Adapter / Platform Service側の責務とする。
- Webではブラウザストレージ、ストア版では適切なネイティブ保存先へ差し替え可能にする。
- 保存先を変更しても、カード・依頼・BOOK記録等のゲーム状態スキーマは共通利用する。
- ゲームロジックから `localStorage.setItem()` 等を直接呼ぶ構造は採用しない。
- アプリ更新後の既存セーブ互換性をA5〜A6のQA対象とする。

## 5. ネイティブ固有機能の扱い【確定】

以下はゲーム進行ロジックへ直接混ぜず、プラットフォームサービスとして扱う。

- アプリ起動・中断・バックグラウンド・復帰。
- Safe Area / ステータスバー。
- 永続ストレージ。
- ハプティクス。
- 共有・通知。
- 将来必要になった場合の課金・ストアSDK。

Web版では不要な機能をno-opまたはWeb用Adapterへ差し替えられる構造を優先する。

## 6. 入力・画面サイズ【確定】

- 基準プレイ体験はスマートフォン縦画面。
- iPhone固有解像度をゲーム状態へ埋め込まない。
- Safe Areaは表示層／プラットフォーム層で吸収する。
- スマホではPointer Eventsを中心とし、PCではマウス／キーボード、必要なら将来ゲームパッドへ拡張できる構造を維持する。
- ストーリー、カード取得条件、依頼条件等を入力デバイス依存にしない。

## 7. アセット【確定】

`pages/development/asset-pipeline.md` の実行用アセット方式を継続する。

- ゲーム本体は制作Wikiのraw URLへ常時依存しない。
- Web / Vercel / ストアラッパーで同じ相対的な実行用アセット構造を利用できるようにする。
- OSローカル絶対パスや特定開発環境のURLへ固定しない。

## 8. 描画とゲーム状態【確定】

主人公、NPC、イベント対象等の位置・状態はゲーム座標として保持し、DOM要素そのものを正本状態にしない。

描画エンジンの全面交換は現在行わない。必要になった場合にDOM / CSS / Canvas等を変更しても、コンテンツ・条件・セーブ・ゲーム座標を再利用できる境界を維持する。

## 9. 開発フローへの影響【確定】

日常の小さなwork unitでは従来どおり、Web/Vercelを高速確認環境として利用してよい。

ただし節目では、Webで動くだけでは完成判定しない。

```text
仕様確定
→ Wiki保存
→ 共通ゲーム実装
→ test / build / CI
→ Vercel高速確認
→ 必要な節目でネイティブ同期・ビルド
→ iPhone実機 / TestFlight確認
→ リリース候補判定
```

ネイティブ確認の詳細は `pages/development/device-test-strategy.md` を正とする。

## 10. プロモーションとの接続【確定】

ストア版とWeb版を競合する配布形態として扱わない。

- ストア版は「買う／入手して遊ぶ製品」。
- Web/Vercelは「知る／触る／紹介してもらうための入口」。

一般体験版やプロモーション依頼用デモでは、UNTOLDの核となる

`探索 → 情報収集 → 記録 → 推理 → 条件達成 → カード化 → 収集`

を短い時間で理解できる範囲を優先する。一方、終盤の真相・No.99 / No.0等、作品価値を損なう重大なネタバレは不用意に含めない。

プロモーション運用の詳細は `governance/promotion-strategy.md` を正とする。

## 11. 今後の実装ルール【確定】

新しいシステムを実装するときは、以下を確認する。

1. ゲームロジックへブラウザ／OS固有APIを直接持ち込んでいないか。
2. セーブ状態と保存媒体を混同していないか。
3. UI操作とゲーム条件を混同していないか。
4. 特定端末の寸法をゲーム状態へ埋め込んでいないか。
5. アセットが特定開発環境の絶対URL／絶対パスに依存していないか。
6. Web確認とストア版確認の役割を混同していないか。
7. 将来描画・入力・保存方式を変更してもゲーム状態とコンテンツを再利用できるか。

## 12. 既存実装への適用状況【実装確認】

2026-09-16、ストア移植性を考慮した既存実装監査を実施済み。実装修正完了点は `98e89dc4fa213b335681aa35df43b84ec6239b95`、監査記録はゲーム本体 `docs/platform-portability-audit.md` に置く。

主な既存対応：

- 図書館内主人公位置・向きをDOM表示からゲーム状態へ分離。
- 自由操作・チュートリアル進行をDOM datasetからゲーム状態へ分離。
- 衝突判定をゲーム座標へ分離。
- ワールド試作の主人公位置・移動計算を描画／Keyboard入力から分離。
- 地形通行判定をブラウザ画像読込から分離。
- PWA登録をplatform層へ分離。
- セーブ形式と保存媒体を別責務として維持。

この時点ではネイティブラッパー自体は未導入。今後は「将来必要なら対応」ではなく、**v1完成工程の中でネイティブ基盤を成立させる**。
