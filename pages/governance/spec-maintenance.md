# 仕様保守・判断基準運用

このページは、UNTOLD Wikiの内容そのものではなく、**仕様をどう増やし、変え、監査するか**の正本です。

ChatGPTやその他のAIが新しい仕様を提案・確定・変更するときは、`governance/criteria-registry.json` とこのページを併用します。

## 目的【確定】

- 既存仕様を後から変更しやすくする。
- 同じ事実を複数ページへ重複保存して、更新漏れが起きるのを減らす。
- 新しい判断基準を後から追加できるようにする。
- 新しい判断基準を、必要に応じて既存仕様へ遡って適用できるようにする。
- 「なぜ変更されたか」「どの基準が影響したか」を追跡できるようにする。
- AIが毎回Wiki全体を読むのではなく、必要な正本へ最短で到達できるようにする。

## 正本を一つにする【確定】

原則として、**一つの仕様事実には一つの正本を置く**。

- 詳細な仕様は話題ごとの個別正本へ置く。
- `README.md`、`pages/chatgpt-guide.md`、`pages/open-items.md`、進捗ページ、索引ページは、必要以上に確定内容を全文再掲しない。
- `ai-index.json` と `ai-current.json` は参照高速化用の非正本ファイルとし、具体仕様本文を複製しない。
- 索引や運用ページでは、できるだけ「どの正本を見るか」を示す。
- 同じ内容を要約として再掲する必要がある場合は、その要約が正本ではないことを明示する。
- 正本が変更されたとき、二重管理された要約が残っている場合は必ず影響確認する。

この原則は、Wikiを短くするためではなく、**変更箇所とAIの探索量を減らすため**に使う。

## 文書の役割【確定】

### 個別正本

世界、町、システム、キャラクター、カードなど、具体仕様の根拠。

### 横断基準

`pages/design-philosophy.md` や `pages/naming-guidelines.md` のように、多数の個別正本へ影響する判断基準。

### ルーター・索引

`AGENTS.md`、`README.md`、`ai-index.json`、`ai-current.json`、`ai-manifest.json`、`pages/chatgpt-guide.md`、`pages.json`。

具体仕様を二重管理せず、「どこを見るか」を決める。

- `AGENTS.md`：AIの最小入口。
- `ai-index.json`：通常回答用の高速ルート表。
- `ai-current.json`：現行マイルストーン・進捗・未確定台帳への短い入口。
- `ai-manifest.json`：詳細ルーティング、補助参照、旧資料、更新規則。
- `pages/chatgpt-guide.md`：ChatGPTの参照・更新・監査運用。

### 未確定台帳

`pages/open-items.md`。

現在も未確定・保留であるものだけを置く。確定事項の一覧表にはしない。

### 進捗・履歴

実装状況、旧仕様、廃止済み資料。

現行のゲーム仕様を上書きしない。

## 判断基準レジストリ【確定】

横断的な判断基準は `governance/criteria-registry.json` に登録する。

各基準は最低限、以下を持つ。

- `id`: 将来も参照できる固定ID。
- `title`: 人間向けの短い名称。
- `status`: confirmed / provisional / retired。
- `source`: 実際の基準本文があるMarkdownと見出し。
- `scopes`: どの種類の既存仕様へ影響しうるか。
- `retroactiveMode`: 既存仕様へどう扱うか。
- `revision`: 基準そのものの改訂番号。

基準本文は原則としてMarkdown側を正本とし、JSONへ同じ長文を複製しない。

## 適用範囲（scope）【確定】

基準を追加するときは、「何に適用するか」を曖昧な自然文だけで終わらせない。

`criteria-registry.json` の `scopeProfiles` を利用し、必要なら新しいscopeを追加する。

scopeは以下の組み合わせで表せる。

- 特定ページ
- 特定ディレクトリ
- 除外ページ
- 内容上の対象に関する注記

例として、会話・イベントの基準を追加する場合、世界設定全体へ無差別に適用するのではなく、`narrative-design` のような対象範囲へ絞る。

## 既存仕様への遡及モード【確定】

### `apply`

新しい基準を**既存仕様にも適用して変更する**。

このモードは、ユーザーが「既存にも適用」「今ある内容もこの基準で直す」など、遡及変更まで明示的に求めた場合に使う。

対象ページを洗い出し、矛盾箇所を修正し、変更したページを `governance/review-ledger.json` に記録する。

### `review`

既存仕様を**監査するが、確定内容は自動変更しない**。

新しい基準を追加しただけで遡及変更の意図が明確でない場合の既定値とする。

対象ページを洗い出し、衝突があれば提示する。ゲーム内容を変える必要がある場合は、別の明示的判断を待つ。

### `future_only`

今後の新規設計・変更にだけ適用する。

既存の正式名称など、過去の確定内容を機械的に作り直したくない基準に向く。

## 新しい判断基準を追加するとき【確定】

1. 基準本文の正本となるMarkdownを決める。
2. `criteria-registry.json` に固定IDを追加する。
3. 適用scopeを決める。
4. 遡及モードを `apply` / `review` / `future_only` から決める。
5. `apply` または `review` の場合、scopeに一致する既存ページを洗い出す。
6. 各ページを基準に照らして確認する。
7. 変更・衝突・例外・未確認を `review-ledger.json` に記録する。
8. ルーティングに影響するなら `ai-index.json` と `ai-manifest.json` を確認・更新する。

**基準を登録しただけで「既存仕様にも適用済み」とみなしてはいけない。**

## 基準を変更するとき【確定】

既存の判断基準の意味が変わった場合は、その基準の `revision` を上げる。

誤字修正など意味を変えない変更では、必ずしもrevisionを上げなくてよい。

意味が変わった場合は、以前に適用済みでも新しいrevisionとして既存仕様への影響を再確認する。

## 遡及レビュー台帳【確定】

`governance/review-ledger.json` は、基準追加・変更によって既存仕様を見直した履歴を残す。

最低限、以下を記録する。

- review ID
- 対象基準IDとrevision
- 適用モード
- 確認したページ
- 実際に変更したページ
- 例外
- 未完了・判断待ちの有無

途中までしか確認できていない場合は `partial` とし、完了したふりをしない。

## 仕様変更の手順【確定】

個別仕様を変更するときは、以下の順で処理する。

1. 話題の現行正本を特定する。
2. `criteria-registry.json` から適用される横断基準を確認する。
3. 関連する他の正本・索引・未確定事項への影響を確認する。
4. 変更する正本を更新する。
5. 古い内容が別ページに残っていないか確認する。
6. 未確定事項が解消・新規発生した場合は `pages/open-items.md` を更新する。
7. ページ追加・削除なら `pages.json` を更新する。
8. 参照ルートが変わるなら `ai-index.json` と `ai-manifest.json` を更新する。
9. 現行マイルストーンや主要な現在地参照先が変わるなら `ai-current.json` を更新する。
10. 横断基準の遡及適用を伴うなら `review-ledger.json` を更新する。

## 高速確定・統合フロー【確定】

会話中に同一話題の設計を連続して進める場合、確定事項ごとにGitHubへ書き込むことは避ける。通常の確定は会話内の**topic buffer**へ保持し、通信回数を減らす。

- `「それで確定」` などの通常確定は原則topic bufferへ追加する。
- topic bufferは会話内だけの非永続領域であり、永続保存が必要な場合は `decision-inbox.md` へまとめて書き込む。
- 同一話題の確定が5件に達してなお検討が続く場合は、5件をDecision Inboxへ1回で中間保存してよい。
- ユーザーが `「記録して」`、`「登録して」`、`「反映して」` と明示した場合も、関連するtopic bufferをまとめてDecision Inboxへ保存する。
- ただし、話題の検討が終了し、統合先が明確な場合はDecision Inboxを経由せず、topic bufferから個別正本へ直接まとめて統合する。
- 同一targetの複数決定はtargetを1回だけ取得してまとめて反映する。
- 複数targetの場合も必要な正本だけを取得し、可能なら複数ファイルを1コミットで反映する。
- 統合先不明、直接矛盾、未確定との衝突がある決定だけはDecision Inboxへ残し、他の統合可能な決定を止めない。
- 同じtopicについてDecision Inboxに既存項目がある場合、topic bufferと合わせて一度に統合してよい。
- 詳細なbuffer・Inboxの優先順位、保存条件、一括コミット条件は `decision-inbox.md` を正とする。

この運用の目的は、仕様の確定精度を落とすことではなく、**同じ話題で何度も同じファイルへアクセスする無駄を減らし、設計会話を止めないこと**にある。

## 確定・暫定・未確定の変更【確定】

- `未確定 → 確定`: 未確定台帳から削除し、個別正本へ記録する。
- `確定 → 変更`: 旧内容を正本に並存させず、必要なら履歴として明示的に分離する。
- `確定 → 未確定`: 理由がある場合のみ行い、以前の確定内容をそのまま現行仕様として残さない。
- `暫定 → 確定`: 暫定表記を残したまま確定扱いしない。
- `廃止`: 現行導線から外し、必要なら履歴へ移す。

## ChatGPTが変更案を出すとき【確定】

ChatGPTは、ユーザーの新しい提案を既存基準へ照らす。

- 問題がなければ、そのまま検討を進める。
- 衝突する場合は、どの基準ID・どの既存仕様と衝突するかを示す。
- 基準そのものを変える方がよい場合は、その選択肢も出す。
- 基準変更が既存仕様へ波及する場合は、その影響範囲も示す。

新しい基準が後から追加されても、過去の仕様を忘れたふりをして今後だけ守る、という便利な記憶喪失は禁止する。

## AI高速参照レイヤーの保守【確定】

- `ai-index.json` は通常回答の高速ルート表として使う。
- `ai-index.json` には具体仕様本文を持たせず、正本へのパスと必要最小限の見出しヒントだけを置く。
- 大きな正本ページで高頻度に参照する箇所は `sectionHints` へ追加できる。
- `ai-current.json` は現行マイルストーンと主要な現在地参照先だけを持つ。セッションごとの細かな作業内容は原則保存しない。
- ルーティングが曖昧な場合は `ai-manifest.json` を詳細フォールバックとして使う。
- `tools/validate-ai-routing.mjs` で高速ルーターと詳細ルーターの参照切れ、主要見出しの不整合を検査する。

## 監査チェックリスト【確定】

Wiki保守では最低限、以下を確認する。

- `pages.json` と実ファイルの対応。
- `ai-index.json`、`ai-current.json`、`ai-manifest.json` の参照先が現存するか。
- `ai-index.json` の `sectionHints` が実際のMarkdown見出しと一致するか。
- `criteria-registry.json` のsource参照先が現存するか。
- `pages/open-items.md` に確定済み内容が残っていないか。
- 管理ページや索引に、個別正本と重複する確定内容が増えていないか。
- 旧名称・旧座標・旧仕様が現行正本へ紛れ込んでいないか。
- 進捗・履歴ページが現行正本として扱われる導線になっていないか。
- 新しい基準の遡及レビューが `partial` / `blocked` のまま放置されていないか。

## `wiki.json` の扱い【確定】

`wiki.json` は旧方式との互換・履歴用であり、現行仕様の正本ではない。

既存Markdownを更新しても同期しない。
