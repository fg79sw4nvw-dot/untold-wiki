# P0：先行リスク解消・成立性検証

**状態：確定**  
**決定日：2026-09-16**  
**更新日：2026-09-16**

このページは、UNTOLDの設計トラックD・アプリトラックAとは別に、**後から判明すると大規模な手戻りにつながる前提を、通常のマイルストーン順序より先に検証するための独立マイルストーン**を定義する。

P0はD/Aを置き換えない。現在のD0「既存設計の統合・棚卸し」と並行して進め、確定済み仕様の範囲だけを使って検証する。

未確定仕様を、検証や実装の都合だけで補完してはならない。

---

## P0の目的

次の4種類の問題は、発見が遅いほど影響範囲が大きくなる。

1. コンテンツ量産後にデータ構造の不足が判明する。
2. 多数のシステム実装後にセーブ構造の変更が必要になる。
3. 大量の画像・マップ・NPCを設計した後に、製品版として成立する制作方法がないと判明する。
4. 序盤・中盤を大量に作った後に、終盤まで一本の物語として成立しないと判明する。

P0ではこれらを早期に検証し、D1〜D4およびA1〜A6の手戻りを減らす。

---

# P0-1：共通データモデルの先行設計・実証

## 対象

少なくとも以下の主要データを対象とする。

- Card
- NPC
- Dialogue
- INFO / OBSERVATION / QUESTION / INFERENCE等の情報ノード
- Quest
- Event
- Location / Region
- Item / Equipment / Spell / Recipe等、他データから参照される主要コンテンツ

## 達成条件

- 各データについて、安定して参照できる固定IDの方針がある。
- 必須項目、任意項目、他データへの参照方法を定義している。
- 1つの会話や情報が複数カード・複数伏線等へ関係できる現行仕様を表現できる。
- 条件、進行状態、地域、NPC、情報、カード等の参照が循環的なハードコードに依存しない構造になっている。
- 代表データを使って、実際のゲームコードから読み込み・参照できることを確認する。
- 将来項目が追加されたとき、既存データ全件を人力で全面書き換えしなくても拡張可能な構造になっている。

ここで確定するのは**データを保持・接続する器**であり、未確定のゲーム内容そのものを埋めることではない。

---

# P0-2：セーブデータ構造・バージョニングの先行設計

## 対象

少なくとも以下の永続状態を検討対象とする。

- 指定カード取得状態
- BOOK記録・情報状態
- NPC会話・条件付き会話の進行状態
- 依頼・イベント進行
- 日付・時刻
- 所持品・装備・スペル等
- プレイヤー状態
- 地域・探索・マップ関連状態
- 各種解放状態
- 進行フラグ

## 達成条件

- 「何を保存するか」と「再計算可能なので保存しないもの」を区別している。
- セーブ内で使用する固定IDがP0-1のデータモデルと整合している。
- セーブデータ自体にバージョンを持たせる。
- 仕様変更・データ変更時のマイグレーション方針を定義している。
- 古いセーブを読み込めない変更を、無自覚に導入しないための運用方針がある。
- 代表状態について、保存 → 再読込 → 状態復元を実証できる。

P0-2では完成版の全状態を先に実装する必要はない。**後から保存方式そのものを作り直さずに済む骨格**を完成させる。

---

# P0-3：アセット制作パイプライン実証

## 目的

完成版で必要になる素材を、単発で作れるかではなく、**同一品質・同一規則で量産し、ゲームへ組み込めるか**を先に確認する。

## 最低検証対象

### NPC

- 基準となるNPCを1人選び、必要な向き・歩行表現をゲーム内で実際に動かす。
- キャラクターの一貫性を保つ制作方法を確立する。
- 将来のNPC増加時に、全員を完全な個別手作業へ依存しない方式を検討・採用する。

### マップ

- 代表マップ1つで、背景画像・通行可能領域・障害物・入口・イベント座標等をゲームロジックと一致させる工程を通す。
- マップ画像の修正時に当たり判定等が破綻しにくい管理方法を決める。

### カード・静止画

- 現行のカードカテゴリから代表例を使い、共通テンプレート・余白・構図・出力形式等を統一できることを確認する。
- No.01〜99を量産するときに品質が大きくばらつかない制作基準を持つ。

### 音

- BGM・効果音について、ChatGPT内で完結しない場合も含め、制作・生成・調達・ライセンス確認・ゲームへの組み込みまでの採用途を決める。
- 外部サービスが必要な場合は、それを明示的な外部依存として記録する。

### PWA容量・実行負荷

- 代表アセットを組み込んだ状態で実際にビルド・配信し、モバイルPWAとして成立することを確認する。
- 問題が出た場合に、画像形式、解像度、遅延読込、キャッシュ等のどの方式で対処するかを決める。

## 達成条件

- NPC、マップ、カード／静止画、音について製品版で採用する制作経路が明確になっている。
- 代表素材が実際のゲーム内で動作・表示・再生できる。
- 大量制作へ入る前に、致命的な制作上の障害がないことを確認している。
- ChatGPT内で完結しない工程がある場合、必要な外部作業と担当範囲が明示されている。

# P0-4：終盤までの物語成立性確認

## 目的

細かなセリフや全イベントを作る前に、UNTOLDが開始から終わりまで**一本のゲームとして終われる構造**になっているかを確認する。

## 確認する骨格

最低限、以下を一本につなげる。

**ゲーム開始 → UNTOLD発見 → 探索・カード収集 → 世界への違和感拡大 → 過去・未開・記録文化封印への接近 → No.99 → No.0 → 主人公の最終判断 → エンディング**

## 達成条件

- 序盤・中盤・終盤・結末の因果関係が一本につながる。
- No.99とNo.0が、単なる追加カードではなく物語上必要な位置を持つ。
- 主人公が最後に判断する問題が、ゲーム中に集めてきた情報と接続している。
- 終盤で必要になる情報や前提を、序盤・中盤へ後から大量に無理やり追加しなくても済む見通しがある。
- プレイヤーに意図的に残す問いと、制作側が決めるべき未確定事項を区別できている。
- D1で詳細化する物語・情報構造に対して、終点側から必要条件を返せる。

P0-4はD1そのものの完成を意味しない。**D1を進めた結果、終盤で成立しないと判明する事故を避けるための先行チェック**である。

---

# P0完了条件

P0-1〜P0-4をすべて満たした状態を、**P0「先行リスク解消・成立性検証」完了**とする。

P0完了時には、少なくとも以下が成立している必要がある。

- 大量コンテンツを載せられるデータ構造がある。
- 長期開発に耐えられるセーブ構造の骨格がある。
- 製品版アセットを実際に作って組み込める制作経路がある。
- UNTOLDが開始からエンディングまで物語として成立する見通しがある。

未解決のリスクが残る場合は、単に「後で考える」とせず、該当するD/Aマイルストーンまたは明示的な未確定事項へ引き継ぐ。

---

# D/Aマイルストーンとの関係

- **現在はD0とP0を並行して進める。**
- P0はD1〜D3の検討と一部重なることを許容する。重複部分は別仕様を作らず、既存正本へ接続する。
- P0-4の結果はD1の入力として使用する。
- P0-1・P0-2の結果は主にD3およびA2以降の基盤として使用する。
- P0-3の結果はD4の大量コンテンツ設計・A3〜A4の素材実装へ入る前提として使用する。
- **D4の本格的な大量コンテンツ制作へ入る前にP0を完了させる。**
- **A4の全コンテンツ実装へ入る前にP0を完了させる。**

P0は「今すぐ全部作る」ためのマイルストーンではない。後から根本設計・保存方式・制作方法・結末を作り直す事態を避けるための、先行リスク処理である。
