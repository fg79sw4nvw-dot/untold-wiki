# ストア版 / iPhone 実機テスト方針

**状態：確定**  
**決定日：2026-09-16**  
**更新日：2026-09-16**

このページは、UNTOLD v1をストア配布を正式な完成形として開発し、iPhone実機・TestFlight・Web/Vercelをどの段階で使い分けるかをD/A/P0マイルストーンへ対応付ける開発運用上の正本である。

2026-09-16に従来の「Safari / PWAを主要完成環境とし、まずWeb版を完成させる」方針を廃止した。以後は、**Vercelを高速確認環境、iOSストア版を第一製品環境**として扱う。

---

## 基本方針【確定】

- 日常の細かな変更はVercelで高速確認する。
- すべてのコミットをネイティブビルド／TestFlightへ流さない。
- 手戻りの種類が変わる節目では、実際のiOSアプリ環境で確認する。
- 基準実機はiPhone縦画面とする。
- Safari / PWA確認はWeb体験版・プロモーション・ブラウザ互換性のために残すが、v1完成判定の最終基準にはしない。
- Androidは再実装不要な構造を維持し、本格実機QAは開発後半で追加する。

---

# 実機テストのチェックポイント

## 0. P0：ネイティブ基盤成立確認【必須】

ストア版前提へ切り替えた後、早い段階で一度だけ以下を成立させる。

- 現行Vite / TypeScriptビルドをネイティブラッパーへ載せられる。
- iPhone実機でアプリとして起動できる。
- タップ・移動入力が成立する。
- Safe Areaで致命的にUIが欠けない。
- 代表アセットが表示される。
- アプリ終了／再起動が成立する。
- バックグラウンド移行／復帰で即座に破綻しない。
- セーブAdapterを差し替えられる構造が成立している。

ここではゲーム全体の完成を要求しない。目的は「完成後に初めてアプリ化できないと判明する」事態を防ぐこと。

## 1. P0-3：Web / Vercel成立確認【必須】

Vercelは引き続き開発・試遊・プロモーションで使うため、Web環境自体も成立確認する。

- iPhone Safariで起動する。
- 基本操作が成立する。
- 縦画面で致命的な崩れがない。
- 代表アセットが表示される。
- 再読込で起動できる。
- 必要なPWA / Service Worker挙動を確認できる。

ただし、このチェックを通過してもストア版完成とは扱わない。

## 2. A1完成判定前：基本プレイ縦切り【必須】

iPhoneアプリ環境で、開始からUNTOLDの基本ループを最低1系統完走する。

最低確認範囲：

- ゲーム開始〜導入終了。
- 通常移動。
- 会話。
- 調査。
- BOOK。
- 記録。
- 推理・条件達成。
- カード化。
- 収集。
- 依頼。
- マップ遷移。
- 日付・時間。
- セーブ・再開。

基本ループ：

`探索 → 情報収集 → 記録 → 推理 → 条件達成 → カード化 → 収集`

を、Webではなくストア版相当の実機環境でも成立させる。

## 3. D3終盤〜A2完成判定前：主要システム・UI統合【必須】

代表確認例：

- BOOKを開く／閉じる。
- 記録・思い出す・情報確認。
- フリーポケット。
- アイテム使用。
- 装備変更。
- スペル。
- MAP / ミニマップ。
- 施設利用。
- 各種戻る導線。
- セーブ・再開。

特に以下を実機で確認する。

- ボタンサイズ。
- スワイプ。
- スクロール。
- 誤タップ。
- 入力競合。
- Safe Area。
- ステータスバー／ホームインジケータ周辺。
- アプリ中断／復帰。
- 視認性。

## 4. A3完成判定前：世界移動・長時間・負荷確認【必須】

iPhoneアプリで30分〜1時間程度の連続プレイを含める。

確認対象：

- 地域間移動。
- 町・屋外・施設の往復。
- 大型マップ。
- 船・確定済み特殊移動。
- カメラ。
- アセット読み込み。
- 長時間プレイ後の重さ。
- メモリ負荷。
- 発熱。
- バックグラウンド移行と復帰。
- OSによる中断後の復帰。
- 長時間タッチ操作の負担。

## 5. A4完成判定前：初の全編ストア版相当プレイ【必須】

新規開始からエンディングまで最低1回、iPhoneアプリ環境で通す。

確認対象：

- 新規開始。
- 序盤・中盤・終盤。
- No.01〜No.99およびNo.0関連進行。
- 地域移動。
- 依頼・イベント。
- 情報導線。
- 自由探索による順序差。
- セーブ・再開。
- エンディング到達。

ここからTestFlight利用を標準候補とする。

## 6. A5：TestFlight中心の本格QA【必須】

A5ではTestFlight等の配布環境を使い、製品版に近い状態で複数回の通しQAを行う。

少なくとも以下を組み合わせて確認する。

- 新規インストール。
- アプリ更新。
- 既存セーブ互換性。
- オンライン／オフライン。
- アプリ終了 → 再起動。
- バックグラウンド → 復帰。
- 長時間放置後の復帰。
- セーブ → 再起動。
- 新規ゲーム。
- 終盤セーブ。
- エンディング。
- 代表的な条件差・順序差・日跨ぎ。
- 操作、表示、パフォーマンス。

必要に応じて、この段階でプロモーション依頼先・先行テスター向けプレビューも実施できる。

## 7. A6：ストア提出用Releaseビルド最終確認【必須】

A6「リリース判定」では、Vercelや開発ビルドではなく**ストア提出対象のReleaseビルド**を基準とする。

最低限、以下を確認する。

`新規インストール → 新規開始 → セーブ → 再開 → 主要進行 → エンディング到達`

加えて、

- アプリアイコン／起動画面等の製品設定。
- 署名・配布設定。
- ストア提出に必要なメタデータとの整合。
- 更新時セーブ互換性。
- リリース阻害バグが残っていないこと。

を確認する。

A6で新規機能を追加しない。

# Work先行テスト → 人間実機QA【確定】

初期〜中盤のテストでは、ユーザー自身が最初からすべての確認を手作業で行わず、**Workに機械的・反復的な確認を先行させ、その後にユーザーがiPhone実機で体験品質を詰める**二段階方式を標準とする。

## Workが先に担当する範囲

最初の2〜3周程度を目安に、Vercel / ローカル開発環境 / 利用可能なブラウザ・シミュレーション環境で以下を確認する。

- 起動と主要画面遷移。
- 新規ゲーム開始〜代表的な基本導線。
- 移動、会話、調査、BOOK、記録、メニュー等の代表操作。
- 押せないボタン、遷移不能、表示欠落、明白なレイアウト崩れ。
- コンソールエラー、例外、読み込み失敗。
- 仕様正本との明白な不一致。
- 同じ確認を繰り返せる項目の回帰確認。

Workの目的は、**人間が触る前に機械的に発見できる粗をできるだけ除去すること**である。

## ユーザーがiPhone実機で担当する範囲

Work先行テスト後、ユーザーが物理iPhoneで以下を重点確認する。

- タップ、スワイプ、スクロールの気持ちよさ。
- ボタンや文字の実寸感。
- 誤タップしやすさ。
- Safe Area、ホームインジケータ、キーボードとの干渉。
- 実端末での重さ、発熱、メモリ感覚。
- アプリ切替、中断、復帰。
- 長時間操作時の疲れや煩わしさ。
- 「仕様上は正しいが、遊ぶと気持ちよくない」箇所。

物理iPhoneでしか判断できない感覚的・端末固有の品質は、Workの確認結果で代替しない。

## フィードバック循環

```text
Work先行テスト
→ 機械的な不具合・明白な仕様不一致を修正
→ ユーザーがiPhone実機でプレイ
→ 体験上の違和感・端末固有問題を抽出
→ Workへ修正・回帰確認を戻す
→ 必要に応じて再度ユーザー実機確認
```

この方式は、ユーザーの実機確認時間を単純なバグ探しに消費せず、**操作感・テンポ・視認性・遊び心地など、人間が判断すべき部分へ集中させる**ために採用する。

# Web / Vercel確認との関係【確定】

Vercelは開発中ずっと重要だが、ネイティブ実機確認の代替ではない。

### Vercelを優先するもの

- セリフ・テキスト調整。
- カード条件・データ調整。
- 一般UI微調整。
- マップ配置調整。
- 通常イベント追加。
- 宣伝用ブラウザ体験版確認。

### ネイティブ実機確認を追加するもの

- Safe Area。
- OSライフサイクル。
- セーブ媒体変更。
- ネイティブプラグイン。
- ハプティクス。
- アプリ中断・復帰。
- パフォーマンス／発熱。
- ストアビルド設定。

毎回両方を要求せず、変更の性質に応じて使い分ける。
