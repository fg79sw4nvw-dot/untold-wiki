# プラットフォーム移植性・ストア対応方針

**状態：確定**  
**決定日：2026-09-16**  
**更新日：2026-09-16**

このページは、UNTOLDを現在のWeb/PWAとして開発しながら、将来必要になった場合にiPhone以外のブラウザ、Android、タブレット、PC、およびApp Store / Google Play向けの配布形態へ移行しやすくするための**実装上の設計制約**を定義する。

これは「今すぐネイティブアプリを作る」という決定ではない。現時点の実装を不必要に複雑化せず、完成後にプラットフォーム対応が必要になった場合の手戻りを抑えることを目的とする。

---

## 1. 基本方針【確定】

- ゲーム本体の正規実装は、当面TypeScript / Web技術を中心に維持する。
- PWAは現在の主要配布・検証形態として扱う。
- 将来App Store / Google Playへ配布する場合も、**ゲームロジック・コンテンツ・セーブ形式を再実装せず、外側のプラットフォーム層を追加する構造**を優先する。
- iOS / Android / PC向けに別々のゲーム本体を持たない。
- 将来のストア配信方式やラッパー技術（Capacitor、TWA、独自WebView等）は、必要になった時点の要件・審査条件・技術状況を確認して選定する。現時点では固定しない。

---

## 2. レイヤー分離【確定】

UNTOLDは原則として以下の4層を分離する。

```text
コンテンツ定義
  カード / NPC / 会話 / 情報 / 依頼 / イベント / 世界データ
        ↓
ゲームロジック
  進行 / 条件 / 時間 / 記録 / 所持 / セーブ状態 / 移動計算
        ↓
表示・入力
  フィールド描画 / BOOK / UI / Pointer / Keyboard等
        ↓
プラットフォーム層
  PWA / ブラウザ保存 / ネイティブラッパー / OS固有機能
```

### 禁止

ゲームロジック層へ、以下を理由なく直接埋め込まない。

- `window`
- `document`
- `navigator`
- `localStorage`
- Service Worker
- iOS / Android固有API
- ストアSDK

ブラウザ・OS固有機能が必要な場合は、UIまたはプラットフォーム層から呼び出す。

---

## 3. セーブと保存先の分離【確定】

`pages/development/save-data-model.md` のセーブスキーマを、保存先そのものから独立させる。

### 原則

- `SaveData` はゲーム状態の交換形式。
- 「どこへ保存するか」は別責務。
- Web/PWAではブラウザ側ストレージを使用できる。
- 将来のネイティブラッパーではOS側のファイル／ストレージへ保存する実装へ差し替え可能にする。
- 保存先を変更しても、カード・依頼・BOOK記録等のセーブ内容そのものは同じスキーマを利用する。

したがって、ゲームロジックから `localStorage.setItem()` 等を直接呼ぶ構造は採用しない。

---

## 4. PWAとストア版の関係【確定】

PWA固有処理はゲーム本体から分離する。

現行 `src/pwa.ts` のようにService Worker登録を独立した入口へ置く方針を維持する。

将来ストア用ラッパーを採用する場合は、必要に応じて以下を差し替える。

- オフラインキャッシュ
- OSライフサイクル連携
- 永続ストレージ
- フルスクリーン／ステータスバー
- ハプティクス
- 共有
- 通知
- 課金等のストア機能

これらは**ゲーム進行ロジックとは別のプラットフォームサービス**として追加する。

---

## 5. 入力【確定】

ゲーム進行は特定端末の入力方式だけを前提にしない。

### 現在

- スマホ：Pointer Eventsを中心としたタッチ操作。

### 将来追加可能

- PC：マウス。
- PC：キーボード移動。
- タブレット：タッチ。
- 必要になった場合：ゲームパッド。

内部の移動・決定・戻る等は、可能な範囲で「入力された操作」としてゲーム処理へ渡し、タッチ座標そのものをゲーム進行条件へ埋め込まない。

ストーリー、カード取得条件、依頼条件等は入力デバイスによって変化させない。

---

## 6. 画面サイズ・Safe Area【確定】

- 基準プレイ体験は引き続きスマートフォン縦画面。
- iPhone固有解像度をゲームロジックへ埋め込まない。
- `env(safe-area-inset-*)` 等を用いてノッチ／ホームインジケータ領域をUI側で吸収する。
- タブレット・PCでは、まず基準ゲーム画面の縦横比を保って安全に表示できることを優先する。
- PC専用ワイドUI等は、必要性が出た時点で表示層として追加し、ゲームロジックを分岐させない。

---

## 7. アセット【確定】

`pages/development/asset-pipeline.md` の実行用アセット方式を継続する。

- ゲーム本体は制作Wikiのraw URLへ常時依存しない。
- ゲーム内参照は同一オリジンまたは明示的なゲーム用配信先を基本とする。
- PWAでもストアラッパーでも同じ相対的な実行用アセット構造を利用できるようにする。
- ファイルパスをOSのローカル絶対パスへ固定しない。

---

## 8. 描画・ゲームロジック分離【確定】

主人公、NPC、イベント対象等の位置・状態はゲーム座標として保持し、DOM要素の位置そのものを正本状態にしない。

これにより将来、必要になった場合に以下を変更可能にする。

```text
DOM / CSS描画
      ↓
Canvas等の描画方式
```

この変更で、以下を再設計しなくて済む構造を維持する。

- NPC定義
- 会話
- 依頼
- 指定カード
- 情報ネットワーク
- セーブデータ
- ゲーム内座標

描画エンジンの全面交換を現在行う必要はない。

---

## 9. 将来ストア配信時の扱い【確定方針】

ストア配信を実際に行う段階で、最新のApple / Googleの審査要件と配布方式を改めて確認する。

その時点で追加する候補は以下。

- iOS / Android用ラッパープロジェクト
- アプリアイコン／スプラッシュ
- OSライフサイクル処理
- ストレージアダプタ
- Safe Area追加検証
- バックグラウンド／復帰テスト
- ストア署名・提出設定
- TestFlight / Google Playテスト配布

ゲーム本体をSwift / Kotlin等へ全面移植することは、別の明示的な判断がない限り前提にしない。

---

## 10. 今後の実装ルール【確定】

新しいシステムを実装するときは、以下を確認する。

1. ゲームロジックへブラウザ／OS固有APIを直接持ち込んでいないか。
2. セーブ状態と保存媒体を混同していないか。
3. UI操作とゲーム条件を混同していないか。
4. iPhone固有寸法をゲーム状態へ埋め込んでいないか。
5. 実行用アセットが特定開発環境の絶対URL／絶対パスに依存していないか。
6. 将来描画方法を変更してもゲーム状態・コンテンツを再利用できるか。

この確認は、将来のストア対応のために現在の開発を重くするものではない。**同じゲーム本体を複数の配布形態へ載せられる境界を守るためのガード**として扱う。
