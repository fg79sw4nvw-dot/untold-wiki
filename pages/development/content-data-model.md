# P0-1 共通データモデル

**状態：P0-1完了**  
**決定日：2026-09-16**  
**更新日：2026-09-16**

このページは、UNTOLDのカード、NPC、会話、情報ノード、依頼、イベント、場所、アイテム等を大量に追加しても、参照関係と保存構造が破綻しないための**共通データモデル基盤**を定義する。

ゲーム内容そのものの正本ではない。個別カード、NPC、世界設定、会話、取得条件等の具体仕様は、それぞれの話題別正本を優先する。

---

## 1. 基本原則【確定】

### 1.1 定義データと実行時状態を分離する

- **定義データ**：カード名、NPC、会話本文、情報ノード、依頼定義、場所定義等、「何が存在するか」を表すデータ。
- **実行時状態**：取得済みカード、進行中依頼、会話回数、所持品、現在時刻等、「現在どうなっているか」を表すデータ。

同じオブジェクトへ両方を混在させない。

これにより、コンテンツ追加・仕様変更とセーブデータ変更を必要以上に連動させない。

### 1.2 IDと表示名を分離する

- 表示名を変更しても参照IDは原則変更しない。
- すでにWiki上で固定IDが存在する場合は、そのIDを優先して使用する。
- 例：`ELD-NPC-010`、`NET-001` 等。
- 指定カードはNo.0〜99の番号自体を安定した識別情報として扱える。
- 同じ文字列IDが異なる種類で存在しても衝突しないよう、参照時は**種類 + ID**で識別する。

### 1.3 データはJSON化可能な形を基準とする

定義データおよび将来セーブ対象となるデータは、原則として以下で表現可能にする。

- plain object
- array
- string
- number
- boolean
- null

`Map`、`Set`、class instance等が必要な場合は、実行時に派生させる。永続化の正本にはしない。

### 1.4 多対多を前提とする

UNTOLDでは一つの情報・会話・NPCが複数のカード、QUESTION、TRUTH、伏線等へ関係できるため、主要な関連を単一参照だけで固定しない。

- 一つのINFOが複数QUESTIONへ接続可能。
- 一つの発言が複数カード情報として機能可能。
- 同じ発言がカード攻略情報と物語上の伏線の両方として機能可能。
- 一つのNPCが複数の情報ネットワークへ属してよい。

### 1.5 未設定と「なし」を区別する

設計上、以下は別状態として扱う。

- `unset`：まだ判定・設計していない。
- `none`：確認したうえで該当情報なし。
- `present`：該当情報あり。

特にNPCのカード情報・伏線情報ではこの区別を必須とする。

## 2. 二層データモデル【確定】

UNTOLDの全コンテンツを、一つの巨大な万能オブジェクトへ統合しない。

### 共通層

すべての参照可能コンテンツが共有する最低限の器。

必須項目：

- `schemaVersion`
- `kind`
- `id`
- `refs`

`refs` は0件でもよいが、項目自体は共通構造として持てるようにする。

### ドメイン層

カード、NPC、会話、イベント、レシピ等に固有のデータ。

- 個別正本ですでに必須と確定しているものだけを必須化する。
- ある種類にしか意味のない項目を、他種類へ空欄として持たせない。
- 後からドメイン固有項目が追加されても、共通ID・参照方式を変えずに拡張できる構造とする。

この方式により、共通参照の安定性と、各システム固有仕様の変更容易性を両立する。

---

## 3. 共通参照モデル【確定】

参照は概念上、以下の形を基準とする。

```ts
{
  kind: "npc" | "dialogue" | "specifiedCard" | "info" | ...,
  id: "固定ID"
}
```

現時点の共通種別は以下。

- `specifiedCard`
- `npc`
- `dialogue`
- `truth`
- `info`
- `observation`
- `question`
- `inference`
- `quest`
- `event`
- `location`
- `region`
- `item`
- `equipment`
- `spell`
- `recipe`
- `clue`
- `hidden`
- `open`

これはゲーム画面上の分類ではなく、制作・実装上の参照種別である。

### 参照役割【確定】

参照には、単に対象IDだけでなく「何として参照しているか」を示す `role` を持たせられる。

例：

- `speaker`
- `quest`
- `clue`
- `location`
- `specified-card`

`role` は固定された一種類の列挙へ閉じず、各ドメインの正本に従って追加できる。

## 4. 種類別の最低必須・任意項目【確定】

ここでは**P0共通基盤として必要な最小線**だけを定義する。個別仕様の完全なスキーマは各正本を優先する。

| 種類 | 共通層以外で最低必須 | 任意・個別正本側で追加する主なもの |
|---|---|---|
| `specifiedCard` | `number`, `name`, `description` | イラスト参照、取得条件、難易度、配置、関連イベント等 |
| `npc` | 表示上識別できる名称または役割名、カード情報・伏線情報それぞれの `unset / none / present` 状態 | 配置、活動時間、移動、通常会話、条件会話、知識・人物関係等 |
| `dialogue` | `text`、発言種別を判別できる情報、記録可能か否か | NPC話者参照、INFO、CLUE、カード、イベント等への複数参照 |
| `truth` / `info` / `observation` / `question` / `inference` | 制作側が内容を識別できる本文または要約 | 他ノードとの接続、関連NPC・場所・会話・カード等 |
| `quest` | 固定ID | 表示名、開始・進行・完了条件、追跡表示、関連カード・NPC・場所等 |
| `event` | 固定ID、開始条件、完了状態を識別する方法、再発可否 | 強制移動、会話、映像、演出、関連NPC・場所等 |
| `location` | 固定ID | 表示名、座標、親地域、入口・出口、マップ遷移、関連施設等 |
| `region` | 固定ID | 表示名、範囲、地形、天候、所属場所等 |
| `item` | 固定ID、表示名、フリーポケット上の分類 | 効果、価格、使用条件、素材属性、画像等 |
| `equipment` | Item相当の必須項目、装備スロット種別 | 装備効果、軽減率、耐性、採取補助等 |
| `spell` | 固定IDまたは安定した番号、効果定義を識別できる情報 | 名称、レア度、使用条件、対象、個別効果パラメータ等。未確定項目は無理に埋めない |
| `recipe` | 固定ID、料理／製作の区分、必要素材と必要数、完成物 | 料理効果、習得経路、表示情報等 |
| `clue` / `hidden` / `open` | 既存台帳の固定ID | 関連INFO・会話・場所・カード等への参照 |

### 補足【確定】

- `quest` は依頼ごとに進行構造が異なるため、P0共通層で一律の「ステップ配列」を必須化しない。
- `location` / `region` は、表示名を持たない内部領域・判定地点を扱えるよう、共通層では表示名を必須化しない。
- `dialogue` は、主人公の心の声・システム文等も扱うため、NPC話者を必須化しない。
- ただし、**別データから参照される会話は必ず固定IDを持つ**。単なるその場限りの演出文は、他データから参照されない限りインライン表現を許容する。
- `spell` は現在一部名称・効果が未確定であるため、全スペルに未確定値を仮入力する目的で厳格な完成版スキーマを先行固定しない。

## 5. 情報ノード接続【確定】

`pages/story/information-architecture.md` の現行仕様をそのまま実装可能にする。

情報ノードは以下の5種類。

- `TRUTH`
- `INFO`
- `OBSERVATION`
- `QUESTION`
- `INFERENCE`

接続は以下。

- `raises`
- `supports`
- `contradicts`
- `resolves`
- `recontextualizes`

`supports` では `weak / normal / strong` の強度を持てる。

必要な接続は `required: true` を持てる。

CLUEは上記ノードと同格にはせず、制作側メタ情報として別参照する。

## 6. NPC情報プロフィール【確定】

NPC情報は、最低限以下を別軸として保持できる構造にする。

### カード情報

管理可能項目：

- 対象カード
- 関連INFO / OBSERVATION / INFERENCE
- 関連会話
- 提示位置：`A / B / C / conditional / event`
- 記録可能か
- 知識状態
- 情報源

### 伏線情報

管理可能項目：

- 対象 `CLUE / HIDDEN / OPEN`
- 知識状態
- 情報源

伏線側には、カード情報と異なり「提示位置」「記録可能か」を必須管理項目として持たせない。

同じ会話・INFOをカード情報側と伏線側の双方から参照してよい。

### 知識状態

- `knows`
- `partial`
- `suspects`
- `mistaken`
- `unknown`

### 開示姿勢

- `open`
- `guarded`
- `concealed`

知識状態と開示姿勢は別軸とする。

## 7. 指定カードの識別【確定】

- No.01〜99は正式な指定カード番号として扱う。
- No.0も特殊な参照対象として共通データモデル上で表現可能にする。
- No.0を通常の1〜99取得コレクションへ自動的に含めることはしない。
- 表示上の番号形式と、実装内部の数値・文字列表現は分離可能とする。
- 実装中の指定カード番号は、複数フローへ数値リテラルを重複させず、カード定義側の固定定数を参照する。

## 8. 参照整合性検証【確定】

大量コンテンツ化に備え、次を自動検査できる構造にする。

- 同一種別・同一IDの重複定義。
- 空ID。
- 存在しないNPC、会話、カード、依頼、情報ノード等への参照。
- 将来的には、循環してはいけない依存関係や取得不能条件も別検証へ追加可能とする。

参照先がまだ未設計だからという理由で、架空の内容を補完しない。未解決参照は検証結果として明示する。
