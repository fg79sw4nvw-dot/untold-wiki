# 制作・実装・配信ワークフロー

## 状態

**確定**  
**更新日：2026-09-16**

## 目的

UNTOLDの制作を、設計・実装・Web確認・ストア版確認・プロモーションが別々に進んで取り残されないよう統一する。

2026-09-16に正式製品をストア版へ変更したため、従来の

`仕様 → Wiki → ゲーム実装 → GitHub → Vercel → Safari/PWA実機確認`

を、以下へ更新する。

```text
仕様確認・確定
→ Wiki保存
→ 表示文面ユーザーレビュー（該当する場合）
→ 共通ゲーム本体へ実装
→ test / build / CI
→ Vercel高速確認
→ 必要な節目でネイティブ同期・ビルド
→ iPhone実機 / TestFlight確認
→ ストア提出用Releaseビルド
```

Vercelは引き続き重要だが、正式製品版の完成環境ではなく、**高速開発・Web試遊・プロモーションのための環境**として扱う。

仕様本文の正本は話題ごとの個別Wikiページ、実装の正本は `fg79sw4nvw-dot/untold-game` / `main` とする。

---

## 役割の分離【確定】

### `untold-wiki` / `main`

- ゲーム仕様・設計判断・制作基準・工程基準の正本。
- 公開Wikiが古くてもGitHub `main` を正とする。

### `decision-inbox.md`

- 会話中に確定したが個別正本へ未統合の事項を一時保管する。
- 通常はtopic bufferを利用し、約10項目、話題終了、明示指示、または実装開始前に正本へ統合する。

### `untold-game` / `main`

- ゲーム本体実装の正本。
- Wikiの確定仕様だけを実装根拠とする。
- 未確定事項を実装都合で補完しない。

### GitHub Actions / CI

- `untold-game` のテスト・ビルド成功を最低条件とする。
- Wiki側はAIルーティング・公開ページ参照等の構造検証を行う。
- CI失敗状態をwork unit完了とは扱わない。

### Vercel

用途：

- GitHub `main` のブラウザ動作確認。
- 日常開発の高速プレビュー。
- 一般向けWeb体験版。
- プロモーション依頼用デモ。
- メディア／配信者向けプレビュー。
- 宣伝素材確認。

VercelのREADYはストア版完成を意味しない。

### ネイティブ / TestFlight

- ストア製品環境に固有の問題を検証する。
- Safe Area、OSライフサイクル、ネイティブ保存、アプリ更新、バックグラウンド復帰等を確認する。
- 細かな全変更ごとに回さず、節目とプラットフォーム依存変更時に使用する。

### App Store / Google Play

- UNTOLD v1の正式製品配布先。
- A6ではストア提出対象Releaseビルドを最終基準とする。

---

## 制作単位【確定】

同じ目的に属する設計変更・Wiki反映・本体実装・検証を1つの **work unit** とする。

例：

- 図書館レイアウト変更。
- No.01取得条件変更。
- BOOK UIのまとまり。
- セーブAdapter追加。
- ネイティブライフサイクル対応。

意味の薄い小分けコミットを大量に作らない。ただし独立検証・復旧性・緊急修正のための分割は認める。

# 標準フロー【確定】

## 0. 作業開始・再開

1. `untold-wiki` / `main` HEAD確認。
2. `untold-game` / `main` HEAD確認。
3. 中断後なら直前の関連コミットも確認。
4. `ai-current.json` から必要な個別正本へ進む。
5. 関係する場合だけ `decision-inbox.md` を確認。
6. Web確認が必要ならVercelの対象SHAを確認。
7. ネイティブ確認中なら、対象ゲームSHAとネイティブビルドの対応を確認。

会話上の進捗表示よりGitHub・Vercel・実ビルド状態を優先する。

## 1. 設計・確認

1. 必要な個別正本だけを読む。
2. 既存実装を変更する場合は関連コードだけ確認する。
3. 必要なら確定前プレビューを作る。
4. ユーザー確定、または既存ルールで許された裁量によって仕様を確定する。

マップ制作では `pages/development/map-preview-workflow.md` を優先する。

### 人物設計の境界

- ストーリー上重要ではない人物は、ChatGPTが自律的に確定してよいのは配置までとする。
- それ以外の人物詳細は `pages/cards/card-roster.md` の「人物設計の裁量境界」を優先する。
- 配置だけを先に確定しても、名前・性格・台詞等を実装都合で補完しない。

## 2. Wiki保存

通常の設計会話：

- 会話内topic bufferで保持。
- 必要ならDecision Inboxへ中間保存。
- 約10項目、話題終了、明示指示で個別正本へ統合。

同じwork unitで本体実装へ進む場合は、**実装開始前までに実装根拠を個別正本へ統合する。**

## 2.5 表示文面の実装前レビュー【必須ゲート】

プレイヤーが実際に読む文面を含むwork unitでは、**共通ゲーム本体へ実装する前に、ユーザーによる文面確認を必ず行う。**

対象には以下を含む。

- NPC台詞
- 主人公の心の声
- カード名・カード説明
- 依頼文
- QUESTION文
- システム文
- 選択肢
- チュートリアル文
- 施設表示
- 通知文
- その他、プレイヤー画面へ表示される文章

レビュー時は、単独の文章だけを見せて終えず、可能な限り以下の文脈を併記または再現する。

- どの画面に出るか
- 直前・直後に何が起きるか
- 誰が話しているか
- その時点でプレイヤーが何を知っているか
- 表示行数・選択肢・カード面等、文章の見え方に影響するUI条件

必要なら、**本体実装とは別のレビュー用モック／プレビュー**を作成して文脈を再現してよい。ただしこれは文面確認用であり、`untold-game` の正式実装完了とは扱わない。

ユーザーが確認・修正した文面をWiki正本へ反映し、**表示文面が確定した後にだけ本体実装へ進む。**

未確認の候補文を、便宜上 `untold-game` / `main` へ先行実装してはいけない。

## 3. 共通ゲーム本体へ実装

1. 確定仕様のみを根拠にする。
2. プレイヤー表示文面を含む場合、**2.5の実装前レビューを通過した確定文面だけ**を使用する。
3. 依存するイベント、NPC、遷移、セーブ、アセット等も確認する。
4. `governance/platform-portability.md` のレイヤー境界を維持する。
5. ブラウザ／OS固有処理をゲームロジックへ直接混ぜない。
6. 未確定仕様が必要になった地点で勝手に補完しない。
7. 検証可能なまとまりでコミットする。

### 実装後の表示確認【確定】

- 実装前レビューを通った文面でも、実装後に改行・文字量・前後演出・表示時間等によって違和感が出る場合は再確認する。
- この実装後確認は、**実装前レビューの代替ではない。**
- 実装後に文面を変更する場合は、意味・条件・情報量が変わらない軽微修正でもユーザー確認を通してから最終収録する。
- 文面変更によって伏線、取得条件、clueId、人物像、ストーリー解釈等が変わる場合は、該当する設計正本も更新する。
- D4で「台詞・説明文完成」と判定する際は、実装前レビューを通過した確定文面が正本に存在することを条件とする。

## 4. GitHub / CI確認

ゲーム更新時：

- `main` が意図したSHAを指している。
- テスト・ビルド・CI成功。
- 確定仕様の取りこぼしがない。

Wiki更新時：

- 正本へ反映済み。
- Wiki構造検証に問題がない。

## 5. Vercel高速確認

Web確認が必要なwork unitでは以下を確認する。

1. 対象Vercelプロジェクトが正しい。
2. デプロイ元が `main`。
3. GitHub SHAが確認対象SHAと一致。
4. デプロイがREADY / success。
5. 必要なら本番ドメインが対象デプロイを指している。

Vercelは以下の確認を高速化するために使う。

- セリフ・データ。
- 通常UI。
- マップ。
- イベント。
- Web体験版。
- プロモーション用デモ。

表示文面については、Vercelは**実装後の文脈・改行・レイアウト確認**に使用する。初回の文面承認は2.5の実装前レビューで済ませてから本体実装へ進む。

## 6. ネイティブ確認

以下に該当する場合、Vercel確認だけで閉じない。

- Safe Area。
- OSライフサイクル。
- 永続保存。
- ネイティブプラグイン。
- ハプティクス。
- バックグラウンド／復帰。
- アプリ更新。
- パフォーマンス／発熱。
- ストアビルド設定。
- `pages/development/device-test-strategy.md` が指定するマイルストーン到達時。

ネイティブ確認では、共通Webビルドをネイティブラッパーへ同期し、iPhone実機またはTestFlightで検証する。

## 7. ストアリリース確認

A5〜A6では日常のVercel確認とは別に、ストア配布工程を進める。

- TestFlight等で本格QA。
- 新規インストール。
- 更新。
- 既存セーブ互換。
- Releaseビルド。
- 署名・配布設定。
- ストアメタデータ・アイコン・スクリーンショット等の整合。
- ストア提出対象ビルドで最終プレイ。

A6達成はVercelの公開成功ではなく、**正式製品としてストア提出可能な状態**を基準とする。

# Vercel運用【確定】

## `untold-wiki`

公開表示に関係しない内部管理更新だけでVercelビルドを消費しない。

通常ビルド不要：

- `AGENTS.md`
- `ai-*.json`
- `decision-inbox.md`
- `.github/**`
- `tools/**`
- 公開表示に使わない内部管理ファイル

公開内容・配信設定の変更は必要に応じてビルドする。

## `untold-game`

`main` はWeb開発確認へ直結するため原則Vercelへデプロイする。

非mainブランチの自動Preview Deploymentは標準では無効とし、必要なwork unitだけ例外にする。

## 制限・失敗時

Vercel障害や制限があってもGitHub `main` の正本性は失われない。

「GitHub反映済み」「Vercel未反映」「ネイティブ未確認」を分離して報告する。

古いREADYデプロイを最新と誤認しない。

---

# プロモーションとの接続【確定】

`governance/promotion-strategy.md` を正とする。

開発工程から、以下を自然に生成する。

- A1：基本ループのゲームプレイ映像。
- A2：主要システム紹介。
- A3：世界・地域・移動素材。
- A4：ストアスクリーンショット／トレーラー候補確定。
- A5：先行プレビュー／プロモーション依頼／TestFlight。
- A6：発売プロモーション。

プロモーション用Webデモは製品本体から分岐した別ゲームとして作らず、共通実装を使い、開始位置・解放機能・体験範囲だけを必要に応じて調整する。

---

# GitHubコミット運用【確定】

### Wiki

- 会話中の細かな確定ごとにコミットしない。
- Decision Inbox / topic bufferを利用する。
- 意味のあるまとまりで正本統合する。
- 公開Wikiに影響しない更新だけでVercelを無駄に回さない。

### Game

- 実機で確認したい関連修正を可能な範囲でまとめる。
- 大きすぎて原因追跡が困難なら独立検証単位へ分ける。
- コミット数ではなく「何を成立させたか説明できる粒度」を基準にする。

---

# 中断・接続切断・別チャットへの復旧【確定】

ストリーミング停止、アプリ再起動、会話切断等が起きても、会話上の表示を完了根拠にしない。

復旧順：

1. Wiki `main` HEADと直前関連コミット。
2. Game `main` HEADと直前関連コミット。
3. 必要なら未完了PR／作業枝。
4. Vercelの最新デプロイとGitHub SHA。
5. GitHub CI/status。
6. 該当正本とDecision Inbox。
7. 必要ならネイティブビルド／TestFlight状態。
8. 「仕様確定」「Wiki保存」「本体実装」「CI」「Vercel」「ネイティブ」「ストア提出」を分離して復元。
9. 最初の未完了工程から再開。

すでに `main` へ入った作業を会話履歴が曖昧という理由でやり直さない。

# 完了条件【確定】

## 設計だけのwork unit

- 確定内容がtopic buffer / Decision Inbox / 個別正本の適切な場所へ保存されている。
- 本体未実装なら必要に応じて明示する。

## Wiki正本更新work unit

- 正本コミット済み。
- 構造検証に問題がない。
- 公開更新が必要ならVercel反映状態を分離して確認する。

## 通常ゲーム実装work unit

- Wiki確定仕様が存在する。
- プレイヤー表示文面を含む場合、**実装開始前にユーザーレビューを通過した確定文面がWiki正本に存在する。**
- Game `main` へ実装済み。
- CI成功。
- Web確認対象ならVercel対象SHAがREADY。
- ネイティブ依存がなければここで閉じてよい。

## ネイティブ関連work unit

通常ゲーム実装条件に加えて、

- 対象ネイティブビルドが成立。
- 必要な実機項目を確認済み。

## A6リリースwork unit

- D5達成。
- A1〜A5達成。
- ストア提出用Releaseビルド成功。
- iPhone実機で最終通し確認済み。
- リリース阻害問題なし。
- ストア提出に必要な設定・素材が揃っている。

これをUNTOLD v1の製品版完成判定とする。
