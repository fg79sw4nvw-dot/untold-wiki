# 制作・実装・配信ワークフロー

## 状態

**確定**

## 目的

UNTOLDの今後の制作を、設計だけ・実装だけ・公開だけが別々に進んで取り残されないよう、**1つの制作単位を「仕様確認 → 確定 → Wiki保存 → ゲーム本体実装 → GitHub検証 → Vercel反映確認 → 必要な実機確認」まで閉じる運用**として統一する。

このページは、Wikiの仕様保守そのものではなく、`untold-wiki`・`untold-game`・GitHub・Vercel・実機確認の間をどう進めるかの工程正本とする。

仕様本文の正本は引き続き話題ごとの個別ページに置き、実装の正本は `fg79sw4nvw-dot/untold-game` / `main` とする。

## 役割の分離【確定】

### `untold-wiki` / `main`

- ゲーム仕様の正本。
- 設計判断、確定仕様、制作基準、工程基準を保持する。
- Vercelで公開されているWikiが古くても、GitHub `main` の内容を正本とする。

### `decision-inbox.md`

- 会話中に確定したが、まだ個別正本へ統合していない事項の一時保管所。
- 通常の高速確定・一括統合ルールは `pages/chatgpt-guide.md` と `pages/governance/spec-maintenance.md` を正とする。
- Vercel公開のために毎回正本統合する必要はない。

### `untold-game` / `main`

- 現在実装されているゲーム本体の正本。
- Wikiにある確定仕様だけを実装する。
- 「Wikiに書いてある」ことと「ゲームで遊べる」ことを混同しない。

### GitHub Actions / CI

- リポジトリ内の自動検証を担当する。
- `untold-game` ではテスト・ビルド成功を最低条件とする。
- `untold-wiki` ではAIルーティング・公開ページ参照等の構造検証を行う。

### Vercel

- GitHub上の状態をブラウザ・PWAで確認するための**配信先**。
- ゲーム仕様や実装状態の正本ではない。
- 「GitHub `main` が更新済み」と「Vercel本番URLへ反映済み」は別状態として扱う。

### `pages/development/implementation-status.md`

- 定期的な実装進捗のスナップショット。
- ライブなHEAD、CI、Vercel状態を代替しない。
- 現在状態を厳密に答える必要がある場合は、ゲーム本体 `main` とVercelを直接確認する。

## 制作単位【確定】

原則として、同じ目的に属する設計変更・Wiki反映・本体実装・確認を1つの**work unit**として扱う。

例：

- 図書館レイアウトを修正する。
- No.01の位置を変更する。
- 会話の表示タイミングを調整する。
- BOOKのUI仕様を1まとまり確定する。

1 work unitの途中で、意味の薄い小分けコミットを大量に作らない。

ただし、以下は分離してよい。

- 設計だけで止めることをユーザーが明示した場合。
- 追加判断が必要で、確定仕様だけでは実装を続行できない場合。
- 修正範囲が大きく、独立して検証できる単位へ分ける方が復旧しやすい場合。
- 緊急修正やリグレッション修正を独立させる必要がある場合。

## 標準フロー【確定】

### 0. 作業開始・再開

1. `untold-wiki` / `main` のHEADを確認する。
2. `untold-game` / `main` のHEADを確認する。
3. 中断後の再開なら、両リポジトリの直前の関連コミットも確認する。
4. `ai-current.json` と必要な個別正本へ最短ルートで進む。
5. 未統合確定事項が関係する場合だけ `decision-inbox.md` を確認する。
6. 実装や実機確認を再開する場合は、Vercelの最新本番デプロイがどのGitHub SHAを指しているか確認する。

会話上の「たぶんここまでやった」より、GitHubとVercelの実状態を優先する。

### 1. 設計・確認

1. 必要な個別正本だけを読む。
2. 既存実装を変更する場合は、必要な範囲だけゲーム本体 `main` を確認する。
3. プレビューや比較が必要なら、確定前の確認用出力を作る。
4. ユーザーの確定、または既存ルールで許された微調整裁量によって仕様を確定する。

MAPについては `pages/development/map-preview-workflow.md` を優先して適用する。

### 2. Wiki保存

通常の設計会話では、既存の高速確定ルールを維持する。

- 会話内topic bufferで保持する。
- 必要なら `decision-inbox.md` へ中間保存する。
- 約10項目、話題終了、または明示指示で正本へまとめて統合する。

ただし、**その確定内容を直ちにゲーム本体へ実装するwork unitでは、実装根拠が必要なため、実装開始前までに対象の個別正本へ統合する。**

同じwork unitのWiki更新は、可能な限り1つの論理的なコミットへまとめる。

### 3. ゲーム本体へ実装

1. Wikiの確定仕様だけを根拠にする。
2. 変更対象だけでなく、依存する当たり判定、イベント、NPC、遷移、セーブ、アセット参照等を確認する。
3. `governance/platform-portability.md` の対象なら、その境界を維持する。
4. 未確定仕様が必要になった地点では補完せず、確定範囲まで実装して停止点を明示する。
5. 同一work unitの実装は、検証可能なまとまりで1コミットを基本とする。

### 4. GitHub検証

ゲーム本体を更新した場合、少なくとも以下を確認する。

- `main` が意図したコミットSHAを指している。
- GitHub Actions / CIが成功している。
- コミットされた内容と、作業対象の確定仕様に明白な取りこぼしがない。

Wikiを更新した場合は、Wiki側の構造検証が成功していることを確認する。

CIが失敗している状態を「完了」と扱わない。

### 5. Vercel反映確認

Vercelを使うwork unitでは、**最新デプロイがREADYであることだけでは足りない。**

以下を照合する。

1. 対象Vercelプロジェクトが正しい。
2. デプロイ元ブランチが `main` である。
3. デプロイのGitHub commit SHAが、確認対象の `main` SHAと一致する。
4. デプロイ状態が `READY` / success である。
5. 必要なら本番ドメインがそのデプロイを参照していることを確認する。

SHAが古い場合、VercelがREADYでも「最新が反映済み」とは扱わない。

### 6. 実機確認

実機確認が必要なwork unitでは、Vercelで対象SHAの本番反映を確認してから行う。

- 表示だけでなく操作・入力・画面サイズ依存・PWA挙動を確認する。
- 実機で見つかった修正は、同じ原因・同じ画面に属するものをできるだけまとめて次のwork unitへ入れる。
- 1px、1文、1タイミングごとにGitHub → Vercelを回すことを標準運用にしない。

## GitHubコミット運用【確定】

### Wiki

- 会話中の細かな確定ごとに `main` へコミットしない。
- Decision Inboxやtopic bufferを利用し、意味のあるまとまりで保存する。
- 正本統合、ルーティング更新、工程更新など同一work unitの複数ファイルは可能な限り**1コミット**へまとめる。
- 公開Wikiの見た目に影響しない内部管理更新だけでVercelビルドを消費しない。

### ゲーム本体

- 実機で確認したい状態まで関連修正をまとめてから `main` へ反映する。
- ただし、大きすぎて原因追跡が難しくなる場合は、独立してテストできる単位に分ける。
- 「コミット数を減らす」こと自体を目的にせず、**1コミットが何を成立させたか説明できる粒度**を基準にする。

## Vercel自動デプロイ方針【確定】

Vercel Hobby環境のビルド枠を、制作上意味の薄いデプロイで消費しない。

### 共通

- 自動デプロイ対象は原則 `main` のみにする。
- 作業枝・復旧枝・実験枝は、明示的に必要な場合を除き自動Preview Deploymentを作らない。
- ブランチ確認が必要な特殊作業では、そのwork unitだけ例外として扱う。

### `untold-wiki`

`main` 更新のうち、公開Wikiの表示内容・配信設定に関係する変更だけVercelビルド対象にする。

通常、以下はVercelビルドを不要とする。

- `AGENTS.md`
- `ai-*.json`
- `decision-inbox.md`
- `.github/**`
- `tools/**`
- 公開表示に使わないルート管理ファイル

`pages/**`、`assets/**`、`pages.json`、Wiki本体UI、`vercel.json` 等の公開内容・配信設定変更はビルド対象とする。

### `untold-game`

`main` の変更は、実機確認・公開動作確認へ直結するため原則としてVercelへデプロイする。

非mainブランチの自動Preview Deploymentは標準では無効化する。

## Vercel制限・失敗時の扱い【確定】

ビルドレート制限、Vercel障害、設定エラー等で最新 `main` がデプロイされない場合：

- GitHub `main` の正本性は失われない。
- Wikiなら「GitHub正本は更新済み／公開Wikiは旧版」と分けて扱う。
- ゲームなら「実装はmainへ反映済み／本番URLは旧版」と分けて扱う。
- 最新SHAが本番へ出ていない状態で、そのURLを使った実機確認を依頼しない。
- 古いREADYデプロイを最新と誤認しない。
- 制限解除後または次の有効なデプロイで、SHA一致を再確認する。

## 中断・接続切断・別チャットへの復旧【確定】

ストリーミング停止、アプリ再起動、会話切断などが起きた場合、会話上の進行表示は作業完了の根拠にしない。

復旧時は次の順で状態を再構築する。

1. Wiki `main` のHEADと直前の関連コミットを確認する。
2. Game `main` のHEADと直前の関連コミットを確認する。
3. 両リポジトリに未完了のPR・作業枝等が関係する場合だけ確認する。
4. VercelでWiki/Gameの最新Production Deploymentと、そのGitHub SHAを確認する。
5. GitHub status / CIを確認する。
6. 該当トピックの正本とDecision Inboxを確認する。
7. 「確定済み」「Wiki保存済み」「本体実装済み」「CI済み」「Vercel反映済み」「実機確認済み」を分離して復元する。
8. 最初に未完了だった工程から再開する。

すでに `main` へ入った作業を、会話履歴が曖昧という理由だけでやり直さない。

## 実装状況ページの更新頻度【確定】

`pages/development/implementation-status.md` はライブ監視表にしない。

更新するのは原則として以下のタイミングとする。

- マイルストーンの到達点が変わった。
- 実装境界が大きく進んだ。
- 実機確認の結果、評価が変わった。
- 長い中断前の引き継ぎとして意味がある。
- ユーザーが明示的に現況スナップショット更新を求めた。

各小コミットごとに更新して、さらにその更新のためだけにVercelを回す運用はしない。

## MAP制作との関係【確定】

MAP制作は `pages/development/map-preview-workflow.md` が具体手順の正本。

MAPについては、同ページの

**仕様整理 → プレビュー → 最終確認 → Wiki確定 → 本体同期・関連処理実装 → 実装後確認 → 必要な実機確認**

を、このページのGitHub / CI / Vercel確認で包む。

つまり、MAPプレビューでユーザーが確定した後は、特別な停止指示がない限り、Wikiと本体の同期だけで終わらず、GitHubと配信状態まで確認してwork unitを閉じる。

## 完了条件【確定】

### 設計だけのwork unit

- 確定事項が会話内・Decision Inbox・個別正本のいずれか適切な場所へ保存されている。
- 「本体未実装」であることが必要なら明示されている。

### Wiki正本更新work unit

- 正本コミット済み。
- Wiki構造検証に問題がない。
- 公開Wiki更新が必要な変更なら、VercelのSHA一致まで確認済み、または公開遅延を明示している。

### ゲーム実装work unit

- Wiki確定仕様が根拠として存在する。
- Game `main` へ実装済み。
- CI成功。
- Vercelを使う確認なら対象SHAが本番へREADY。
- 必要な場合だけ実機確認まで完了。

これらを満たしていない段階では、「GitHub反映済み」「Vercel反映待ち」「実機未確認」のように工程を分けて報告する。
