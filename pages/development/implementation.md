# ChatGPT実装仕様・引き継ぎ

このページは、将来ChatGPTがこのWikiだけを読んでUNTOLDを実装できる状態にするための入口。

## ChatGPTが最初に読む順番【確定】

UNTOLDについて設計・回答・実装を行う場合は、原則として次の順番で確認する。

1. `README.md`
   - 正本リポジトリ、Wiki構成、更新方式を確認する。
2. `pages/design-philosophy.md`
   - イベント、会話、演出、ストーリー、世界観との整合を判断するための共通原則を確認する。
   - ユーザー提案を含め、設計思想・世界観・確定仕様との矛盾をどう扱うかもこのページを正本とする。
3. この `pages/development/implementation.md`
   - ChatGPTがWikiをどう参照・更新し、ゲーム本体へどう実装するかを確認する。
4. 話題に直接関係する各Markdown
   - 個別のシステム、カード、NPC、町、世界、ストーリー等の確定仕様を確認する。
5. 主人公の反応・感情・人格が関係する場合は `pages/story/protagonist.md` も参照する。

同じルールを複数ページで重複管理しない。内容判断の原則は `pages/design-philosophy.md`、ChatGPTの参照・更新・実装運用はこのページを正本とする。

## ChatGPT参照・更新運用ルール【確定】

- UNTOLDについて**仕様・設定・過去の確定事項に関わる回答や設計を行う際は、まず GitHub の `fg79sw4nvw-dot/untold-wiki` の `main` にある関連Wiki本文を参照する。**
- 単なる相づち、直前の発言内容だけで完結する確認、その他明らかにWiki参照が不要な応答では、機械的な参照を省略してよい。
- `確定`、`一旦`、`案`、`未定`を混同しない。状態の意味と全体的な更新ルールは `README.md` を基準とする。
- 会話上の記憶とWikiが食い違う場合は、原則としてWikiの確定記述を優先する。
- 会話中に新しく確定したが、まだGitHubへ反映していない事項は、その後の会話では未反映の確定事項として併用する。
- Wikiと会話中の新しい確定事項が食い違う場合は、勝手に統合・補完せず差分を明示する。
- 実装時に不足する仕様は推測で固定せず、未確定事項として扱う。
- イベント、会話、演出、ストーリー、世界観との整合判断は `pages/design-philosophy.md` を必ず参照する。
- GitHubへの書き込みは、仕様が1項目決まるたびには行わない。
- **確定事項を原則5項目ためた時点で、一括してGitHubへ反映する。**
- 一括更新時は、関連するMarkdownや `pages.json` など、必要なファイルをまとめて更新する。
- 可能な限り細かな連続コミットを避け、Vercelの不要なデプロイ回数を増やさない。
- 5項目未満でも、大きな話題の区切り、会話終了時、ユーザーから明示的に更新指示があった場合は、その時点で一括更新してよい。
- GitHubへ反映した内容は、その時点からWikiの正式な正本として扱う。

## 実装上の共通基準【確定】

- 実装根拠にはWiki上の確定仕様のみを使用する。
- 未確定事項を、ゲームとして自然だから・一般的だから・実装上便利だからという理由で補完しない。
- 画像の基準はエルドの「基本ゲーム画面」。写実・写真調ではなく、温かい手描き2DファンタジーRPG調を優先する。
- ゲーム本体のコードは `fg79sw4nvw-dot/untold-game` で管理し、Wikiリポジトリへ混在させない。

## ゲームの核

**探索 → 情報収集 → 記録する情報の選別 → 推理 → 条件達成 → カード化 → 収集**。

指定カード99種の収集がゲームの大きな目的。戦闘は最低限で、探索・情報収集・推理・発見の気持ちよさを主役にする。

## 基本ゲーム画面・縮尺基準【確定】

- 通常フィールド、町、NPC、建物、道、家具、小物などのビジュアル縮尺は、`assets/game-screen-reference.webp` の縦画面・俯瞰視点・温かい手描き2DファンタジーRPG調を基準とする。
- 主人公の**表示上のスプライト幅は40〜48px前後**を基準レンジとする。背景に埋もれない視認性を優先しつつ、過度に大きくしない。
- 主人公の**移動・衝突判定に使う基準幅は32px前後**とする。見た目のスプライト幅と当たり判定幅は分離して扱う。
- 移動距離を扱う内部基準として、**1歩＝32px移動**と定義する。足アニメ1回や入力1回を1歩とは数えない。
- 主人公の通常移動速度は**110px/s**を基準とする。
- 現在のワールド全体基準は**16000×10000px**、メイン島の最大横幅は**およそ10000px**を目安とする。
- 今後マップを設計する際は、主人公の32px基準幅と110px/sの移動速度から、道幅、建物間隔、町の広さ、探索距離、施設間の所要時間を決める。
- 今後NPCを設計する際は、通常の成人NPCは主人公と大きく乖離しない画面上サイズを基準とし、子供・巨体・特殊種族など意図がある場合のみ明確に差を付ける。
- ドア、ベッド、机、樽、採取物、木、看板などの環境物も、主人公の表示サイズを共通の縮尺基準として設計し、マップごとに人物と建物の比率がばらつかないようにする。
- 具体的な主人公スプライト画像、身長換算、NPC個別サイズ、各建物の実寸pxは必要に応じて後から個別確定する。

## 現在の軽量クラフト方針【確定】

- UNTOLDには**軽いクラフト要素**を導入する。
- クラフトはゲームの主役ではなく、探索やサバイバルを支える補助システムとして扱う。
- クラフトはどこでも行える方式ではなく、**特定の施設でのみ可能**とする。
- 基本系統として、調合・工房・調理などの施設を想定する。
- 主人公自身が施設を使って制作する。NPCへ制作を依頼する方式を基本にはしない。
- 制作費・施設利用料は不要とする。
- クラフトに失敗判定は設けず、条件を満たせば必ず成功する。
- 基本条件は、**レシピ習得済みであること**と**必要素材を所持していること**。
- 使用した素材は制作時に消費する。
- 主人公がNPCから知識を学び、自分で作れるものが増えることを、主人公の成長表現の一部とする。

### レシピ習得【確定】

- この世界では記録文化が失われているため、レシピを本・レシピ帳・メモなどの記録物から習得する方式は原則使わない。
- レシピの習得元は**NPCとの会話**または**依頼を通じてNPCから教わること**を基本とする。
- 依頼報酬としてレシピを得る場合も、紙を受け取るのではなく、NPCから作り方そのものを教わる表現とする。
- 未習得レシピは、クラフト画面に最初から一覧表示しないことを基本とする。

### アイテム入手経路と経済【確定】

- 「購入するしかない」アイテムをできるだけ減らす。
- 食料、回復薬、探索用品、装備などの多くは、購入以外にもクラフト、依頼報酬、探索など別の入手経路を持たせる。
- 一方で、**クラフト限定アイテム**や**依頼限定アイテム**も一部用意してよい。
- スペルカードの**パックはショップ専売**とし、原則としてジェニーで購入することでのみ入手する。
- パックがランダム入手であることから、ジェニーの主要な使い道・温存先として機能させる。
- 通常品については、「ジェニーを払って手早く買う」か「知識と素材を使って自作する」かを選べる構造を基本とする。

### 町ごとのクラフト施設【確定／詳細保留】

- すべての町にすべてのクラフト施設を置くことは避ける。
- **ヴェルノク**は例外的に主要なクラフト施設が一通り揃う都市とする。
- その他の町には、各地域の産業・環境・文化に合ったクラフト施設を配置する。
- 一部の町には、その土地でしか作れない限定クラフト品を設定してよい。
- 町限定クラフト品は大量に用意せず、**各対象町に数種類程度**の例外的な存在とする。
- 大半のレシピは、習得後に対応する同系統施設であれば別の町でも制作できる方向とする。
- **スカルド**には鍛冶の町としての特性を活かした限定装備を置く方向とする。
- **ネメリア**には薬草・調合文化を活かした限定の薬を置く方向とする。
- 限定品は単なる上位互換ではなく、その土地の素材・技術・環境と結びつける。
- 各町にどの施設を置くか、具体的な限定品やレシピは今後個別に決める。

### クラフトUI・制作フロー【確定】

- クラフト施設では、**習得済みレシピのみ**を一覧表示する。
- 未習得レシピはクラフト画面に表示しない。
- 各レシピには固有の**レシピNo.**を割り振る。
- 一覧では、まず**現在作成可能なレシピを上部**へまとめ、その後に素材不足などで作成できない習得済みレシピを表示する。
- 各グループ内では**レシピNo.順**で並べる。
- レシピを選択すると、完成品の名称・イラスト・効果・必要素材・素材の所持数などを確認できる。
- 一度に複数個まとめて制作できる。
- 制作可能な最大数は、**必要素材の所持数とフリーポケットの空き枠**の両方から自動計算する。
- 制作数は最大数以内でプレイヤーが指定する。
- 一括制作時は、指定数ぶんの素材をまとめて消費し、完成品を指定数ぶんフリーポケットへ追加する。
- 制作完了時は長い演出を入れず、施設に応じた**短い演出**と「○○を3個作成した」などの**簡単な結果表示**のみとする。

### ブックのレシピ一覧【確定】

- BOOKに**レシピ一覧ページ**を追加する。
- レシピ一覧はクラフト実行用ではなく、習得済みレシピの確認用とする。
- 表示するのは**習得済みレシピのみ**とする。
- 未習得レシピは空欄や番号だけの枠も含めて**完全に非表示**とする。
- レシピ総数はプレイヤーに表示せず、全部で何種類存在するか分からない状態を維持する。
- 習得済みレシピはレシピNo.順で確認できる。
- レシピ詳細では、少なくとも **No.／名称／完成品イラスト／効果／必要素材／対応施設／教わったNPCまたは入手経路** を確認できる構造とする。
- 実際の制作はBOOKからは行えず、対応するクラフト施設でのみ行う。

### 素材入手・採取ポイント【確定】

- 素材は、入手方法と価値の違いから、**自然素材系**と**獣素材系**を明確に分けて扱う。
- 植物、木材、鉱石などの自然素材は、マップ上に配置した**固定の採取ポイント**から入手する。
- 通常の採取ポイントは、原則として**1種類の素材を固定で産出**する。
- 一部の特殊な採取ポイントでは、基本素材に加えて**低確率で希少素材**が混ざる構造を採用できる。
- 自然素材には**地域限定素材**を設ける。
- **季節限定素材**も採用できるが、種類は少数に絞り、採取の主軸にはしない。
- 採取ポイントは、周囲の景観から「ここで採取できそう」と分かる見た目を基本とし、完全な隠しポイントにはしない。
- 獣素材は、動物・モンスターとの**フィールドエンカウント**の成功報酬として入手する。
- 自然素材はクラフト用途を主とし、売却価格は**かなり低め**に設定する。
- 獣素材はエンカウントによるHP損失・状態異常などのリスクを伴うため、自然素材より**明確に高めの売却価値**を持たせる。
- 特殊素材については、依頼・イベントなど別経路で入手する余地を残す。
- 採取ポイントは一度採取すると一時的に採取済み状態となる。
- 再採取可能になるまでの時間は**現実時間12分**とする。
- リポップ判定はゲーム内時間とは切り離し、宿屋での時間スキップ、時間変更・季節変更スペルなどでは短縮・即時復活しない。
- 実時間経過を基準とするため、ゲーム内時間が停止しているメニュー中やアプリを閉じている間も経過時間として扱う。

### 採取量【確定／装備補正は保留】

- 1回の採取で得られる基本個数にはランダム幅を持たせる。
- 基本確率は以下とする。
  - **1個：85%**
  - **2個：13%**
  - **3個：2%**
- 基本の最大採取数は3個とする。
- 採取量や複数個入手確率を上げる装備を将来的に導入する方向性はあるが、**具体的な補正率・対象素材・装備種類は現時点では保留**とする。

## 現時点の共通カード化表現

- カード化前は原則として正式名称を表示しない。
- 遺物は条件が揃った対象地点を小さな光で示すことを基本とする。
- 生物は正体判明前には黒い影などの抽象表現を使える。
- 人物カード対象者は通常NPCと見た目で区別しない。
- カード化成立時は画面全体を暗転。
- カードが画面下からスライドインし、中央でNo.・名称・画像・説明文を表示する。
- 派手な魔法陣や過剰な粒子演出は原則使わない。


## 指定カードUI実装仕様【確定】

- 指定カード99種は共通の2:3縦長テンプレートを使用する。分類ごとにテンプレートは分けない。
- カード面に表示するのは番号・名称・イラスト・説明文のみ。
- 分類（遺物／生物／人物）は内部データとして保持するが、ゲーム内カード面には原則表示しない。
- 名称は必ず1行。長い場合は軽度の自動縮小を許容し、それでも収まらない名称は名称側を調整する。
- 説明文は最大4行。
- フォントは `Zen Old Mincho` を第一候補とし、`Noto Serif JP`, `serif` をフォールバックとする。
- カード内の具体的な余白・配置は、正式テンプレート画像 `assets/card-template-reference.jpg` を視覚基準とする。
- 未取得時はカード枠を描画せず、空の位置に番号だけを表示する。
- カード化演出とブック閲覧では同じカードコンポーネントを再利用する。
- 実装資産は「共通カードテンプレート＋カードデータ＋カード用イラスト素材」に分離する。完成カードの一枚絵をゲーム実装の正本にしない。
- カード用イラスト素材は必ず1:1の正方形で生成する。
- イラストの縁はぼかし、少し透過感を持たせて紙面へ馴染ませ、イラスト専用枠は付けない。
- 正式なカード視覚テンプレートは `assets/card-template-reference.jpg`。
- 取得場所、関連記録、関連NPC、関連イベント等はカード面ではなくブック側の別UIに表示する。

カードデータ例：

```json
{
  "id": 3,
  "name": "雨を知らない石",
  "category": "relic",
  "illustration": "assets/cards/003-rainless-stone.webp",
  "description": "雨の中でも、不思議と濡れることのない石。ありふれた姿をしているが、その表面にはどこか違和感がある。"
}
```

## データ実装の推奨方針

完成版では設定とゲームロジックを分離する。

- `cards`：カード定義
- `npcs`：NPC定義
- `locations`：マップ・施設
- `clues`：会話・観察から得る情報
- `records`：プレイヤーがブックへ記録した情報ID
- `quests`：依頼状態
- `flags`：イベント進行
- `inventory`：所持品
- `time` / `season` / `weather`：環境状態

カード化条件は可能な限りデータ駆動にし、個別カードのためだけのハードコードを減らす。

例：

```json
{
  "id": 3,
  "name": "雨を知らない石",
  "category": "relic",
  "requirements": {
    "records": ["rainless_stone_rumor", "rainless_stone_location"],
    "weather": "rain",
    "location": "TBD"
  }
}
```

### 実装済み：ワールド・移動基盤

- `16000 × 10000px` の確定ワールド座標系。
- `assets/elden-terrain-mask-final.svg` を使用した確定基礎地形マスク表示。
- 主人公の通常移動速度 `110px/s`。
- 主人公の表示上の幅 `44px`。確定基準レンジ `40〜48px` 内の開発用表示であり、正式スプライトではない。
- 衝突判定幅 `32px`、足元基準の通行判定。
- キーボードとスマートフォン用方向ボタンによる移動。
- 数値座標が確定済みの8都市を開発用に表示。
- 具体ルートが確定済みの4街道を表示。
- 位置・向き・長さが確定済みの3橋を表示。
- 3橋について、通行可能幅 `96px` を使った徒歩通行上書きを実装。
- 水域は徒歩通行不可とし、橋の範囲だけ通行可能にする基礎処理。
- ゲーム開始地点を勝手に確定しないため、起動時は確定座標の町から選ぶ「開発用起点選択」として分離。

### 実装済み：BOOK・所持品・記録基盤

- 指定ポケットNo.01〜99を、`3列 × 3行 × 11ページ` で表示。
- 指定ポケットの矢印ページ移動と左右スワイプ。
- 未取得位置はカード枠を出さず、番号だけを表示。
- BOOK内に、フリーポケット、記録、レシピ確認用の最小開発UIを用意。
- フリーポケットの7分類と180枠。
- 素材以外は1枚につき1枠、素材だけは同種を1スタックとして管理。
- 素材スタック上限99個。100個目以降を取得せず消滅させる処理。
- 満杯時に新しいカードを自動破棄せず、整理が必要な状態を返す処理。
- 装備中カードをフリーポケット180枠の外で管理。
- 着用枠×1、汎用枠×2の装備・入れ替え・取り外し処理。
- フリーポケット満杯時に装備を外せない処理。
- 記録99件上限。
- 1記録に複数の `clueId` を保持できる構造。
- 記録削除時、同じ `clueId` を持つ別記録が残っているかを保持数で判定する処理。
- 記録の検索・並べ替え・グループに対応できる基礎データ構造。

### 実装済み：時間基盤

- 現実1秒をゲーム内2分として進める時間エンジン。
- 24時間制。
- 1季節3日、春→夏→秋→冬の循環。
- 朝・昼・夕・夜の確定時間帯区分。
- 時間停止状態と季節変更時に1日目へ移動する処理。
- 初期時刻・初期季節が未確定のため、ゲーム画面のHUDにはまだ接続していない。
